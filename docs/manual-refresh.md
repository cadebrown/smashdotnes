# Refresh the illustrated manual

The Book uses untouched 256×240 MAME captures. Arrows and short labels are
separate SVG, with their coordinates and wording in
`web/src/data/manual-scenes.json`.

## After game or menu changes

From the repository root, with Rust, cc65, MAME, Node, and the locked web
packages installed (`npm --prefix web ci`):

```sh
make manual-refresh
```

This rebuilds the ROM, drives `nessy/tools/emulator/manual_capture.lua` through
real controller inputs, validates every PNG, and creates a candidate in
`out/reports/manual-refresh/`. It does not replace the Book's approved pictures.

1. Open `out/reports/manual-refresh/index.html`. Compare every changed frame,
   arrow destination, input label, and note. Check that tiny projectiles and hit
   sparks remain visible under the ink. The captured-state notes help explain
   each frame; they do not replace visual inspection.
2. Adjust `web/src/data/manual-scenes.json` as needed. Coordinates use the
   original 256×240 frame. Run `make manual-review` after annotation-only edits.
   If the requested state is wrong or missing, fix the Lua drive and run
   `make manual-refresh` again.
3. Promote the inspected set and exercise the actual site:

```sh
make web-sync
make manual-accept
make test-web
```

Review the generated Book screenshots in `out/reports/web/screens/`, including
the jump sequence, fighters, hit, and mobile layouts. Open `/book/` and click
through the contents and controller overlays. Commit the driver, scene data,
`web/src/data/manual-capture-lock.json`, and `web/public/assets/captures/*.png`
together when the release is ready.

## After website layout changes only

Run `make test-web` and inspect its desktop/mobile screenshots. Unchanged game
pixels do not need recapturing. If keyboard mappings change, also update the
manual's input labels and verify them against the running player.

`make manual-check` runs during every site build. It rejects a different ROM,
capture driver, annotation file, image set, or image bytes than the approved
lock. It also checks dimensions, missing scenes, duplicate labels, and off-frame
coordinates. A stale lock must be refreshed, never bypassed to make a build pass.

The candidate records ROM and image hashes, Git revision/dirty state, and the
observed game state. Each PNG follows its recorded predicate by one game tick,
so prepared OAM has reached the display. The drive never writes game RAM.
Controller photography and decorative paper textures are separate assets and
are not regenerated by this recipe.
